# Диагностика: ComfyUI-Prompt-Assistant — русская локализация и управление окнами

**Дата:** 2026-11-09
**Исходная точка (upstream):** commit `e0587e6` (merge PR #79), версия `2.0.6`, ветка форка `feature/russian-localization-ux`.
**Рабочий каталог:** `F:\Projects\ComfyUI-Prompt-Assistant-RU` (клон форка impxiii; origin → impxiii, upstream → yawiii).

Статус причин: ✅ подтверждено чтением кода; ⚠️ гипотеза (нужна живая GUI-проверка).

## 1. EN → RU переводит на китайский (P0)

### Причина 1.1 — нода `✨Prompt Translate` (подтверждено)
`node/translate_node.py:251`:

```python
to_lang = "en" if target_language == "English" else "zh"
```

Combo `target_language` содержит только `["English", "Chinese"]` (строка 60). Любое значение,
кроме `English`, молча превращается в `zh`. `Russian` выбрать невозможно.

**Изменение:** добавить `Russian` в options; явная карта `{English→en, Russian→ru, Chinese→zh}`;
неизвестное значение → понятная ошибка (никогда не молча `zh`).
Совместимость workflow: V3 `io.Combo` сериализует само строковое значение опции
(проверено в `comfy_api/latest/_io.py`, class Combo.Input.as_dict → `"options": [...], значение = строка`),
поэтому старые значения `English`/`Chinese` сохраняются, `Russian` — новая опция. Локализованные
подписи даются через `locales/*/nodeDefs.json` (`options: {"English": "Английский", ...}` — уже существует).

### Причина 1.2 — определение языка не знает кириллицу (подтверждено)
`node/translate_node.py:_detect_language`: кириллица не попадает ни в "чистый английский"
(`[ -~]+`), ни в "содержит китайский" → `auto`. Функционально не ломает перевод, но:
лог направления неверен; skip-логика ("текст уже на целевом языке") не срабатывает для русского.
**Изменение:** явная поддержка `ru` (`[\u0400-\u04FF]`) в детекторе ноды и на фронтенде.

### Причина 1.3 — фронтенд-кнопка «Перевод» жёстко zh↔en (подтверждено)
`js/utils/promptFormatter.js:289-386 detectLanguage()`:
- чистый английский → `to='zh'` всегда — **это и есть «EN → RU фактически переводит на китайский» у кнопки в текстовом поле**;
- кириллица не распознаётся вовсе: русский текст попадает в ветку «смешанный» с `cnUnits=0, enUnits=0` → `from='zh', to='en'` (RU→EN «работал» случайно, с неверным from);
- серверные эндпоинты (`/llm/translate`, `/llm/translate/stream`) передают `from`/`to` без ограничений — ограничение только во фронтенде.

**Изменение:** распознавание кириллицы; выбор целевого языка:
`UI-локаль ru` (или новая настройка `PromptAssistant.Features.TranslateTargetLang`) → `en→ru`, `zh→ru`, `ru→en`;
иначе прежнее поведение zh↔en (без регрессии для существующих пользователей).

### Причина 1.4 — активное правило перевода по умолчанию «ZH» (подтверждено)
`services/llm.py:537`: `active_prompts.get("translate", "ZH")`. Созданное пользователем русское
правило не активируется само — менеджер правил поддерживает «активацию» одного правила для всех
направлений, и активным остаётся ZH. Шаблон `config/system_prompts_template.json` содержит только
одно правило перевода `ZH`.

**Изменение:**
1. В шаблон добавлены строгие правила `EN_RU` и `RU_EN` (bump `__config_version` 2.1 → 2.2 —
   доставка существующим установкам через deep-merge мигратора; пользовательские правила не трогаются).
2. `services/llm.py`: выбор правила по направлению — если активное правило не менялось
   пользователем (id = `ZH` по умолчанию) и существует правило с id `EN_RU`/`RU_EN`, берётся
   оно; явная активация пользователем имеет приоритет; финальный фолбэк — встроенная инструкция
   в коде (не зависит от состояния конфига).
3. `_LANG_NAMES` уже содержит `ru` — оставлено, уточнено на «Russian (Русский)».

## 2. Окна: «Настройки» перекрываются старым экраном (P0)

Подтверждённая структура слоёв:

| Слой | z-index |
|---|---|
| ComfyUI диалог (PrimeVue `.p-dialog` + mask) | ~1100 (динамически) |
| `.popup_container` (панели PA) | **10180 (статика)** |
| `.settings-modal-overlay` | 10199 статика / `ComfyUI_z+9` инлайн |
| `.settings-modal` | 10200 статика / `ComfyUI_z+10` инлайн |
| выпадашки/меню/tooltip | 10205…10230 (статика) |

### Причина 2.1 — ReferenceError при переключении popup (подтверждено)
`js/utils/popupManager.js:37-74 showPopup()`: используются переменные `oldPopup` и
`oldPopupInfo`, которые в методе **не определены** (остаток рефакторинга). Любое переключение
«открытый popup → другой popup» бросает `ReferenceError`:
- старый popup остаётся в DOM без обработчиков (его listeners уже вычищены строкой выше);
- `_isTransitioning` остаётся `true` навсегда (сброс в строке 71 не выполняется) — ломает
  логику сворачивания контейнеров (`AssistantContainer`);
- новый popup не открывается вовсе.

### Причина 2.2 — жёсткая иерархия z-index при открытии ComfyUI-диалога (подтверждено кодом, воспроизведение ⚠️)
Модалки PA (API-менеджер/Правила, `disableBackdropAndCloseOnClickOutside: true` — без overlay)
и popup-панели PA имеют z-index 10180–10210, т.е. **всегда выше любого ComfyUI-диалога (~1100)**.
Если открыть «Настройки» ComfyUI, пока открыта модалка/панель PA, — окно настроек открывается
**под** окнами PA и ввод в него невозможен. Это в точности сценарий «старый экран остаётся
поверх нового и перехватывает ввод; после ручного закрытия старого экрана настройки работают».

### Причина 2.3 — окно «в полупрозрачном» состоянии перехватывает клики (подтверждено кодом)
`.settings-modal.modal-hide` и `.settings-modal-overlay.overlay-hide` задают `opacity: 0;
visibility: hidden` с `transition: all .3s`. При CSS-переходе `visibility` переключается
в конце анимации: все 300 мс закрывающееся окно остаётся видимым (полупрозрачным) и
**продолжает получать клики** — «прозрачная ловушка». Аналогично закрывающиеся popup
(`popup-closing-*`) — там `pointer-events: none` уже есть, а у модалок — нет.

### Причина 2.4 — инлайн z-index зависит от «первого попавшегося» `.p-dialog` (подтверждено)
`createSettingsDialog` → `getComfyUIDialogZIndex()` берёт `document.querySelector('.p-dialog')` —
первый в DOM, который может не быть тем диалогом, над которым нужно открыться; при
нескольких диалогах/модалках stacking непредсказуем. Единая политика слоёв отсутствует
(спецификация ТЗ §3: «не смешивать navigate и modal stack»).

### Причина 2.5 — Esc и фокус не управляются (подтверждено)
`createSettingsDialog` не добавляет обработчик Esc и не управляет фокусом: Esc закрывает
popup PA (`handleEscKey` в popupManager молчит при наличии `.settings-modal`), но саму
модалку не закрывает никто; фокус не перемещается в модалку.

### Причина 2.6 — новый фронтенд ComfyUI блокирует body (подтверждено ЖИВЫМИ замерами)
В ComfyUI с новым (Radix/Tailwind) фронтендом при открытии диалога «Настройки» сам
фронтенд ставит **инлайн** `document.body.style.pointerEvents = 'none'`. Все окна PA —
прямые дети `body` и **наследуют запрет кликов**: окно видно, но кнопки/поля/скролл
не реагируют, пока не закрыт чужой диалог. Именно это пользователь видел на рис. 4/5.
Замер в живой странице: `.settings-modal` — computed `pointer-events: none` при
`body.pointerEvents: none`; в `elementsFromPoint` над модалкой верхней оказывалась
Radix-маска настроек (`fixed inset-0 z-1700`), а не содержимое модалки.

**Изменение:** явный инлайн `pointer-events: auto` на всех окнах/меню PA (модалка,
overlay, popup-панели, контекстные меню) — он восстанавливает кликабельность поддерева
независимо от состояния body.

### Причина 2.7 — прозрачный фон модалок (подтверждено ЖИВЫМИ замерами)
`.settings-modal` использует `background-color: var(--p-dialog-background)`, но в новой
теме ComfyUI **все токены `--p-dialog-*` не определены** (замер: пусто для background /
border-color / color / shadow / border-radius) → фон окна был `rgba(0, 0, 0, 0)`
(«прозрачный экран» на рис. 4/5). При этом `--p-content-background` (#18181b),
`--p-content-border-color`, `--p-text-color` определены.

**Изменение:** каскадные фолбэки в правиле `.settings-modal` + скоуп-определение токенов
`--p-dialog-*` на поддереве модалки (кастомные свойства наследуются дочерним элементам,
чужую тему `:root` не трогают).

### Причина 2.8 — min-height выталкивал окно за экран (подтверждено живым замером)
`.settings-modal.api-config-dialog-v2 { min-height: 760px }`: при высоте окна браузера
720 px правило `min-height` побеждает `max-height: 90vh` (648 px) → окно высотой 760 px
выходило за границы экрана на ±20 px (замер: rect.y = -20).

**Изменение:** `min-height: min(760px, calc(100vh - 24px))`.

### Причина 2.9 — детект чужих диалогов не видел Radix-диалоги
`getComfyUIDialogZIndex()`/первичный rebase искали только `.p-dialog`/`.p-dialog-mask`
(PrimeVue). Окно «Настройки» нового фронтенда — Radix-диалог (`fixed z-1700`, computed
z-index 1701/1702), его детект не срабатывал.

**Изменение:** `isForeignModalOpen()` — универсальный маркер (body inline
`pointer-events: none` ИЛИ наличие `.p-dialog`); `getForeignDialogTopZ()` сканирует
крупные fixed-элементы не из плагина; наблюдатель слоёв следит также за изменением
`style`/`class` у `body`.

## 3-бис. Причина уровня установки: ДВЕ копии плагина (подтверждено живым сервером)

В `custom_nodes` одновременно находились `prompt-assistant` (старая копия оригинала) и
`ComfyUI-Prompt-Assistant` (форк). Обе копии регистрируют одни и те же V3-ноды; побеждает
первая зарегистрированная — замер живого сервера: `/object_info/PromptTranslate` отдавал
`options: ['English', 'Chinese']`, хотя форк содержал новый код. Также обе копии
обслуживают свой `/extensions/<имя>/index.js` (двойной JS). После отключения старой
копии (переименование) и перезапуска сервер отдаёт `['English', 'Russian', 'Chinese']`.

Дополнительно (живой замер, не относится к плагину): бейджи «版本/使用教程/交流反馈» —
внешние картинки shields.io с текстом в URL (атрибуция оригинального автора), словарной
локализации не подлежат; имена сервисов в табах API-менеджера («智谱», «调用本地模型») —
данные пользовательского конфига, а не системные строки UI.


## 3. Китайские строки в русской локали (P1)

Архитектура: `uiI18n.js` — DOM-локализация по точному совпадению китайского текста с ключом
`locales/ru/ui.json` (flat map «китайская строка → перевод»). Аудит (скрипт, 25 JS-файлов):

- 303 уникальные пользовательские китайские строки; **33 отсутствуют в `ru/ui.json`**
  (позиции панелей в настройках, меню справки узлов, копирование caption, статус-сообщения тегов/видео-инструмента);
- фолбэк локали: `uiI18n.js:109-122` — при недоступной/неполной локали откат **на `zh`**,
  поэтому незнакомые ключи показываются иероглифами вместо безопасного английского;
- динамические строки (`已切换到: ${name}`, `翻译缓存${status}` и т.п.) не локализуются по
  определению точного совпадения — требуется переход на `tUI()`-шаблоны;
- справка узлов (`nodeHelpTranslator.js`) переводит только zh↔en (`dataset.targetLang='zh'`) —
  русский недоступен как целевой;
- `locales/ru/nodeDefs.json` покрывает все 5 нод; при добавлении `Russian` в Combo ноды
  перевод подписи нужно добавить во все локали.

Нет. Все дефекты UI подтверждены чтением кода (точные файлы/строки выше); живое воспроизведение
в ComfyUI-браузере в рамках этой среды недоступно. Ручные сценарии проверки вынесены в
`docs/TEST_REPORT_RU.md` (раздел «Не проверено автоматически»).
